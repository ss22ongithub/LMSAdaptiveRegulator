# MLP Adaptive Regulator — first runs on Raspberry Pi 4 (2026-10-26)

First end-to-end runs of the MLP-based memory bandwidth regulator (`areg.ko`, MLP build)
on a Raspberry Pi 4, with three SPEC CPU 2017 benchmarks running **alone on an isolated core**.
No victim/hog co-runs and no LMS runs yet; those come next.

> **Status: exploratory.** Every number below is from a **single run** per configuration,
> with no repeats. Treat differences under ~10% as noise until repeats are done (see
> [Caveats](#7-caveats)).

## 2. Explainers

**Memory bandwidth via L2 counters.** Each Pi 4 core has a 1 MB L2 cache, the last cache before
DRAM. Two hardware events count the traffic between L2 and memory:

| Event | Code | Meaning | Regulator calls it |
|---|---|---|---|
| `L2D_CACHE_REFILL` | `0x17` | a 64-byte line fetched from memory into L2 | read bandwidth |
| `L2D_CACHE_WB` | `0x18` | a modified 64-byte line written back to memory | write bandwidth |

Bandwidth = (refill + write-back) × 64 B ÷ time. This is also exactly what the MLP predicts.
The Pi 4 has no memory-controller counters, so this is the closest available measure.

**IPC (instructions per cycle).** Instructions retired ÷ cycles. It shows how
efficiently the code runs while it's actually running. Memory stalls lower it.

**How the regulator works.** Every 2.27 ms the master thread (core 0):
1. reads 7 counters on each regulated core
2. feeds the per-interval rates into the MLP, which predicts the next interval's bandwidth
3. turns the prediction into a **budget**: at least `initial_bw_mb`, at most `max_bw_mb`, split
   between read and write in the ratio of the last interval
4. programs the budget into the read and write counters

If a core uses up its **read** budget before the next tick, an overflow interrupt fires. The core
either gets extra budget from a shared **pool** (built up from unused budget), or is
**throttled**: a high-priority kernel thread occupies the core until the next tick.

**Regulating vs. observe-only.**

| | Regulating (default) | Observe-only (`observe_only=1`) |
|---|---|---|
| Measures and predicts every tick | yes | yes |
| Budget given to the core | prediction, capped at `max_bw_mb` | always the full `max_bw_mb` |
| Throttling | yes | none in practice (cap set far above demand) |
| Used to measure | the full regulator's behaviour | model accuracy and pure module overhead |

Observe-only matters because throttling distorts the bandwidth the model is trying to predict:
a throttled core can't use more than its budget, so its usage looks artificially flat.

**Prediction metrics.**
- **Correlation**: does the prediction move with the actual bandwidth? (1 = perfectly, 0 = unrelated).
  Reported per tick and averaged over 100 ticks (~0.25 s).
- **Bias**: average (predicted − actual). Negative = predicts too low.
- **Median error**: median of |predicted − actual| ÷ actual.
- **"Same as last interval" baseline**: predict that the next interval equals the last one. A
  predictor is only useful if it beats this. Reported as *MLP error ÷ baseline error* (below 1 =
  MLP better).

All prediction metrics compare the prediction made at tick *k* with what was actually used at tick *k+1*.

## 4. Baseline (no module, alone on core 3)

| Benchmark | Runtime `baseline` | Runtime `baseline2` | IPC | Read | Write | **Total bandwidth** |
|---|---|---|---|---|---|---|
| lbm | 137.2 s | 161.5 s | 0.395 / 0.371 | 1,503 | 1,106 | **2,609 MiB/s** |
| bwaves | 25.7 s | 25.8 s | 0.569 / 0.567 | 1,759 | 366 | **2,125 MiB/s** |
| mcf | 36.3 s | 36.4 s | 0.404 / 0.403 | 1,971 | 62 | **2,033 MiB/s** |

(IPC given as `baseline` / `baseline2`; bandwidth from `baseline2` only.)

**Takeaways**
- Every benchmark uses **2–2.6 GiB/s** when running alone, far above the old 1000 MiB/s cap.
- **lbm was 18% slower in `baseline2`** (161.5 s vs 137.2 s), with the same 96.53 billion
  instructions and the same 1.8 GHz clock. bwaves and mcf barely changed. The only
  obvious difference is start temperature: 53 °C vs 76 °C. The leading hypothesis is that
  LPDDR4 refreshes more often when hot, which costs bandwidth. That would hit the most
  bandwidth-hungry benchmark hardest. **Not proven.**

## 5. MLP regulating (default cap 1000 MiB/s)

| Benchmark | Runtime | Slowdown vs `baseline` | Slowdown vs `baseline2` | Start temp |
|---|---|---|---|---|
| lbm | 182.4 s | 1.33× | 1.13× | 61.8 °C |
| bwaves | 30.3 s | 1.18× | 1.17× | 70.6 °C |
| mcf | 47.5 s | 1.31× | 1.30× | 73.5 °C |

What the trace showed (core 3):

| | lbm | bwaves | mcf |
|---|---|---|---|
| Ticks where the budget sat at the 1000 cap | 99.6% | 89.0% | 99.0% |
| Throttle events | 54,813 | 6,291 | 8,221 |
| Reclaim interrupts (extra budget from the pool) | 54,721 | 5,274 | 5,133 |
| Read used ÷ read budget | 2.2× | 1.9× | 1.7× |
| Write used ÷ write budget | 2.2× | 1.8× | 1.5× |
| Read/write budget split (MiB/s) | 601 / 397 | 811 / 160 | 960 / 37 |

**Findings**
1. **The cap decided the outcome, not the model.** The MLP predicted ~1.9–2.0 GB/s for lbm, close
   to what it needed. But the budget sat at the 1000 MiB/s cap on 89–99.6% of ticks, so the core was
   throttled constantly. The slowdowns measure the cap.
2. **Enforcement leaks.** Cores used 1.5–2.2× their budget, even on reads (the side that
   triggers throttling). The write budget is never enforced (no overflow callback). The reclaim
   path keeps handing out extra budget.
3. **The reclaim path causes interrupt bursts.** Each reclaim re-arms the counter to overflow
   after only a few events: about 55,000 interrupts on core 3 during lbm.
4. **The pool** grows to millions while cores are idle (35 million before lbm started), then the
   reclaim bursts drain it within about a minute of load.
5. **The read/write split works as designed:** the budget followed each benchmark's mix.
6. **`perf` can't measure IPC under the module.** The module holds all 7 of core 3's counters;
   `perf` got about 1 ms of counter time in 182 s and scaled the rest. Those IPC values are
   invalid, and the script now reports `NA` in that case.

## 6. MLP observe-only (no throttling)

### Overhead

| Benchmark | `baseline2` | `mlp_observe` | Difference | Start temp (b2 / obs) |
|---|---|---|---|---|
| lbm | 161.5 s | 152.2 s | −5.8% | 76.4 / 64.2 °C |
| bwaves | 25.8 s | 26.5 s | +2.6% | 76.9 / 75.0 °C |
| mcf | 36.4 s | 40.3 s | **+10.7%** | 77.9 / 75.0 °C |

- Nothing was throttled on core 3 during the benchmarks. The budget stayed at 10,000 MiB/s on every tick.
- Tick period: median **2.270 ms**, p99 2.32 ms, worst 7.1 ms.
- **The overhead isn't measurable yet.** lbm ran *faster* with the module loaded, which can only
  be noise: it started 12 °C cooler. So temperature effects are as large as the overhead itself.
- **The mcf +10.7% may be real.** Each tick the module sends about **9 cross-CPU interrupts
  (IPIs) to core 3**: 7 counter reads + 2 budget updates, about 4,000/s on the benchmark core.
  Pointer-chasing code like mcf is sensitive to interruptions.

### Bandwidth measurement check
The module's own bandwidth measurements agree with `perf` (from `baseline2`) to within ~4%:

| | Module (observe run) | perf (`baseline2`) |
|---|---|---|
| lbm | 2,701 MiB/s | 2,609 MiB/s |
| bwaves | 2,056 | 2,125 |
| mcf | 2,058 | 2,033 |

### Prediction accuracy (core 3, unthrottled)

| | lbm | bwaves | mcf |
|---|---|---|---|
| Correlation, per tick | 0.93 | 0.83 | 0.87 |
| Correlation, ~0.25 s average | **1.00** | 0.90 | **0.97** |
| Bias | **−269 MiB/s (−10%)** | +15 | **+185 (+9%)** |
| Median error | 10.1% | 12.6% | 26.1% |
| Ticks under-predicted by >10% | 52% | 29% | 29% |
| Ticks over-predicted by >10% | 0% | 41% | 61% |
| MLP error ÷ "same as last interval" error | 5.9 | 2.9 | 6.1 |

**Findings**
1. **The MLP follows the bandwidth trend well on all three benchmarks**
2. **It has a consistent offset**: about 10% low on lbm, 9% high on mcf. A steady offset like this
   points to a calibration mismatch between training and today's runs, which can be corrected.
3. **"Same as last interval" is 3–6× more accurate per tick.** At 2.27 ms these workloads change
   slowly, so repeating the last value is a hard baseline to beat. Whether the MLP or LMS
   beats it is the central question for the comparison.
4. Correction to the first run: mcf looked untrackable there (correlation −0.13), but that came from
   throttling flattening its usage, not from the model.

## 7. Caveats
- **Single runs.** No repeats, so run-to-run variation is unknown.
- **Temperature drift.** Runs started anywhere from 53 °C to 78 °C. lbm's runtime varied by 18%
  between two baseline runs. Alternating the order of configs (baseline, MLP, baseline, MLP …)
  in the repeats would spread this drift evenly.
- **Debug trace on.** Both MLP runs had `trace_printk` logging. In the regulating run much of it
  was printed on core 3 itself (277,000 throttle/reclaim lines), which inflates its runtimes.
- **Inputs differ in size.** lbm uses `train`; bwaves and mcf use `test`.
- **Only core 3 is isolated.** Victim/hog co-runs will need `isolcpus=1-3`.
- **No IPC under the module yet.** It needs the module to export its own instruction and cycle totals.

## 8. Next steps
1. **One cross-CPU interrupt per tick instead of ~9:** read all 7 counters and set both budgets in
   a single call on the target core. Likely reduces mcf's overhead; also applies to LMS.
2. **LMS runs:** regulating, and observe-only (same parameters added to LMS) for a like-for-like
   accuracy comparison, including against the "same as last interval" baseline.
3. **Fix enforcement in both trees:** pool growth, reclaim units and interrupt bursts, write budget.
   LMS's `msleep(1)` actually waits ~4–8 ms on this HZ=250 kernel, so LMS needs hrtimer pacing to really run at 1 ms.
4. **Per-core stats in debugfs:** ticks, throttles, throttled time, prediction error, loop time,
   instructions and cycles (for IPC under the module).
5. **Repeats** (3–5, alternating order) to get real overhead and variation numbers.
6. **Set realistic budgets:** measure the Pi's sustainable bandwidth before the victim/hog experiments.
